# 결정점 (Decision Points): 한 흐름을 세 사람이 보는 방식

상태: 탐색 시안 · 실제 환자·병원 검증 전
시안: 캔버스 '결정점' 페이지 `F3Loop.dc.html`

## 1. 무엇을 찾았나

### 처음 가설을 의심한 결과

처음 가설은 "환자가 '배란 유도 7일째', '21시 주사', '토요일 초음파'가 한 과정이라는 걸 모른다"였다. 하지만 과정 자체는 병원 안내문에 이미 나와 있다(서울대병원 안내: 2~3일 간격 초음파 → 난포 터뜨리는 주사 → 34~36시간 뒤 채취 → 2~5일 배양 → 이식 → 11~12일 뒤 혈액검사). 그래서 모르는 것은 **순서가 아니라 조건**이라고 판단했다.

- 다음 날짜들은 아직 정해지지 않았다. 다음 검사 결과가 그 날짜들을 정한다.
- 토요일 초음파는 채취하는 날이 아니라 **채취 날을 정하는 검사**다. 그 의미는 결과가 나오기 전까지 고정되지 않는다.
- 이 조건을 아는 사람은 병원뿐이다. 환자는 그날 오후 전화로 듣고, 배우자에게 다시 설명한다.

### 근거와 그 한계

| 주장 | 근거 | 한계 |
|---|---|---|
| 채취일은 검사 결과로 정해지고, 트리거 뒤 34~36시간에 채취한다 | 서울대병원 환자 안내 | 병원마다 기준이 다르다 |
| 배우자의 실제 일정(정액 채취, 휴가)은 채취일에 묶여 있다 | 서울대병원 안내("채취일 당일 남편 정액 채취") | 금욕 기간은 병원마다 다르다 |
| 배우자는 과정에서 소외감을 느낀다 | Zaake 2019, 남성 18명 인터뷰 ('feeling insignificant') | 저자원 환경이고 표본이 작다 |
| 환자는 병원이 준 정보를 먼저 믿고, 부족하면 밖에서 찾는다 | BMC Women's Health 2024, 15명 | 고학력·단일 기관 |
| 병원은 채취일을 주말 등 운영 사정에 맞춰 트리거 날을 하루 옮기기도 한다 | 주말 회피 연구 여럿. 하루 이동은 대체로 영향 없음, 이틀 이상은 불리할 수 있음 | 대부분 후향적이다. 업무량 예측은 시뮬레이션 수준이다 |

**"배우자가 토요일이 검사인지 채취인지 구별하지 못한다"를 직접 보여 주는 인터뷰는 찾지 못했다.** 구조상 생길 수 있는 혼동이지만 검증된 사실은 아니다.

## 2. 하나의 객체: 결정점

```text
결정점 = { 무엇을 보고 (초음파·피검사 / 배아 확인),
           언제 결과가 나오고 (토 오전 판독 → 오후 연락),
           누가 정하고 (담당의 / 연구실),
           결과에 따라 열리는 갈래 (하루 더 → 다시 검사 | 트리거 → 이틀 뒤 채취),
           그 갈래가 정하는 날짜 범위 (월~수) }
```

같은 결정점을 세 사람이 다르게 본다. 데이터 원천은 하나다.

| 보는 사람 | 보는 것 | 보지 않는 것 |
|---|---|---|
| 환자 | 지나온 길(실선), 지금(파란 점), 다음 갈림길(◇), 갈래 두 개, 날짜 범위(빗금) | 병원 인력 사정, 다른 환자 |
| 함께 보는 사람 | 다음에 무엇이 정해지는지, 언제 알 수 있는지, 채취·이식처럼 자기에게 걸린 날, 병원 안내 | 환자가 허락하지 않은 투약·수치·대화. 할 일 목록 |
| 병원 | 날짜별 확정(칠한 칸) + 가능(빗금 칸), 결정 대기열(언제, 누구의 무슨 결과가 무엇을 나누는지) | 환자 쪽 감정·사용 여부 추정 |

## 3. 화면 원칙

- **진행률로 그리지 않는다.** 검사 한 번 더는 같은 갈림길을 한 번 더 지나는 것이다. '하루 더' 갈래는 처음부터 그려 두고, 그 길로 가면 날짜 범위가 옆으로 밀릴 뿐이다. '지연', '뒤처짐' 같은 말은 쓰지 않는다.
- **확정과 가능을 눈으로 구분한다.** 확정은 칠하고 실선으로, 가능은 빗금으로. 가능 범위는 문장이 아니라 날짜 띠로 보여 준다.
- **투약 시각에는 흐름이 물러난다.** 창이 열리면 화면 전체가 시각, 약, 용량, '맞았어요'가 되고, 흐름은 한 줄로 줄어든다. 트리거 날에는 '정각'이 맨 위에 온다.
- **배우자에게는 다음 결정의 시각을 보여 준다.** "토요일 오후에 채취일이 정해져요"가 첫 문장이다. 정해지면 환자와 같은 순간에 알린다. 환자가 다시 설명하지 않게 하려는 것이다.
- **공유 범위는 환자가 고른다.** 기본은 '흐름만'이고, '흐름+투약'과 '끔'이 있다. 배아 수 같은 결과 수치는 기본으로 공유하지 않는다.

## 4. 병원: 결정 달력

예약표에는 확정된 시술만 있다. 하지만 "월요일 채취 인원은 토요일 오전 판독에서 정해진다"는 지식은 코디네이터의 머릿속에 있다. 결정 달력은 이 지식을 화면으로 꺼낸다.

- 날짜마다 확정과 가능 인원을 함께 보여 준다. 가능 범위는 여러 날에 걸칠 수 있다(같은 사람이 월·화·수에 모두 빗금으로 나온다).
- 대기열은 **결과가 나오는 시각 순서**로 정렬한다. 그래서 어느 검사 결과가 어느 날 인력을 정하는지 보인다.
- 이 화면이 바꾸는 행동은 셋이다.
  - 연구실에 범위를 미리 알린다 ("월 0~5명").
  - 다음 날 인력에 걸린 환자부터 판독한다.
  - 결과가 나오는 즉시 인력을 확정한다.

### 운영 사정이 임상 판단을 밀어내지 않게 하는 장치

1. 결정 달력은 임상 결정의 **결과를 읽는 화면**이다. 트리거 날짜를 옮기거나 분산하는 기능은 두지 않는다.
2. 트리거·채취 결정을 기록할 때 근거를 고른다: '임상 근거' 또는 '일정 사유 포함'. 일정 사유가 들어가면 담당의 서명이 필요하고, 원장 주간 검토에 올라간다.
3. 병원의 '가능' 범위는 환자에게 확정 일정으로 내보내지 않는다. 환자가 보는 범위는 병원이 승인한 프로토콜 범위("트리거 뒤 이틀째 아침")에서 계산하고, 인력 사정은 반영하지 않는다.
4. 환자 화면에는 확정된 시각만 나온다. 결정 근거는 병원 감사 기록에만 남는다.

## 5. 데이터 계약 추가

```text
DecisionPoint   id, cycleId, kind: monitoring | lab_check | result,
                inputs[] (ultrasound, e2, embryo_check), expectedResultAt, owner (staffRole),
                branches[{ key, label, opensWindow: { from, to } }], status: pending | decided,
                decidedBranch?, decidedAt?, reason: clinical | includes_scheduling, approvedBy?
ShareScope      patientId, viewerId, level: off | flow | flow_doses, includesLabNumbers: false
```

- 날짜 범위(`opensWindow`)는 병원 설정(`protocol_template`)의 규칙으로 계산한다. 모델이 추론하지 않는다.
- 결정점은 병원 콘솔에서 생기거나(병원 연동), 대화로 들은 다음 검사 일정에서 생긴다(독립 모드). 독립 모드에서는 갈래를 병원 안내문 템플릿에서 가져오고, '병원 확인 전'으로 표시한다.

## 6. 아직 모르는 것 (실제 사용 전 검증)

1. 배우자가 실제로 무엇을 헷갈리는가. 위의 혼동 사례는 구조상 추정이다. 부부 인터뷰로 확인해야 한다.
2. 날짜 범위를 보여 주면 불안이 줄어드는가, 오히려 날짜에 매달리게 되는가. 특히 범위가 반복해서 밀릴 때.
3. 병원이 결정점과 결과 예상 시각을 매번 입력할 수 있는가. 코디네이터의 실제 업무 흐름(EMR, 판독 순서)에서 몇 초가 드는지.
4. 국내 병원의 결정 시점이 실제로 이 모양인가. 오전 판독 → 오후 전화가 일반적인지, 병원마다 얼마나 다른지.
5. 결정 달력이 실제로 인력 배치를 앞당기는가. 아니면 이미 코디네이터 머릿속으로 충분한가.
6. 배아 수를 환자 화면에 숫자로 보여 줄지. 결과 보호 설정과 어떻게 맞출지.
7. 근거 기록('일정 사유 포함')을 의료진이 받아들일지. 규제·노무 관점의 검토가 필요하다.
