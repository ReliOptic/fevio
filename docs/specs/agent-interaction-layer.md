# 커튼 = 에이전트 대화 계면 (Agent Interaction Layer)

Status: Draft for review (2026-11-19)
Related: `docs/specs/care-input-and-dosing-flow.md` (§4를 이 문서가 대체), `CLAUDE.md` (AI and automation boundary), `docs/01-product/fevio-product-north-star.md`

> 표기 규칙: **[근거]** 외부 자료·레포 문서로 확인, **[가설]** 검증 필요, **[결정 필요]** 팀 결정.

---

## 0. 요약

1. 커튼은 '사진 올리는 칸'이 아니라 **뒤에 모델이 연결된 대화 계면**이다. 위에서 당겨 내리면 지금 상황에 맞는 첫마디로 대화가 시작되고, 짧게 주고받으며 구조화된 결과(바뀐 처방, 투약 기록, 진료 전 정리, 병원에 보낼 질문)를 함께 만든다.
2. 대화의 산출물은 항상 **눈에 보이는 구조화 결과**다. 커튼 위쪽에 '정리 중' 칸이 고정되고, 대화가 진행될수록 채워진다. 확정은 사용자가 한다.
3. 대답은 **선택지 우선**이다. 키보드는 필요할 때만 올라온다. 대부분의 턴은 칩 한 번 또는 음성 한 마디로 끝난다.
4. 모델은 **추출, 되묻기 선택, 병원 승인 자료 인용**만 한다. 용량 추론, 진단, 위험도 판단은 하지 않는다. 위험 신호는 병원이 정한 규칙으로 판정하고, 모델은 답만 모은다.
5. 병원이 모델을 연결하면, 이 계면은 **병원 대신 매일 짧게 인터뷰하는 창구**가 된다. 병원은 다음을 얻는다.
   - 진료 전 정리된 환자 보고
   - 승인된 답으로 해결되는 반복 질문
   - 맥락이 붙은 문의 대기열
   - 처방 변경을 환자가 이해했는지에 대한 확인 기록
   - 병원 기준에 따른 위험 신호 연결
6. 모델이 실패하거나 꺼져 있으면 **수동 입력 화면**(`care-input-and-dosing-flow.md` §3-2의 '무엇이 바뀌었나요?')으로 그대로 이어진다. 수동 흐름은 AI 없이도 완결된다(CLAUDE.md).

## 1. 이전 결론 수정

`care-input-and-dosing-flow.md` §4에서 "커튼은 입력에 쓰지 않는다"고 했다. 근거는 '자유 텍스트 입력 + 키보드'였다. 커튼을 대화 계면으로 다시 정의하면 문제가 달라진다.

- 대화의 대부분은 칩과 음성이라 키보드가 없다.
- 키보드가 필요할 때만 커튼이 전체 높이로 펼쳐지고, 입력줄이 키보드 위에 붙는다.
- 수동 입력 화면은 없어지지 않는다. 대화가 채우는 구조화 결과가 곧 그 화면이고, 언제든 '직접 고치기'로 넘어갈 수 있다.

## 2. 무엇을 주고받나 — 대화 다섯 가지

커튼을 열면 지금 상태(단계, 시각, 최근 진료, 미확인 투약)를 보고 아래 중 하나로 시작한다. 사용자가 다른 걸 말하면 그쪽으로 바뀐다.

### A. 진료 뒤 정리 (가장 중요)

시작 조건: 진료 예정 시각 + 30~60분, 또는 사용자가 연다.

```text
Fevio  진료 끝났어요? 바뀐 게 있으면 지금 정리해 둘게요
       [그대로예요] [바뀌었어요] [사진으로] [말로 할게요]
나     (말로) 고날에프 150으로 줄이고 내일부터 세트로타이드 추가,
       토요일 아침에 다시 오래
Fevio  이렇게 들었어요
       ┌ 정리 중 ───────────────────────┐
       │ 용량  과배란 주사A  225 → 150 IU │
       │ 추가  억제 주사  내일부터        │
       │ 진료  토 · 시각 ?               │
       └──────────────────────────────┘
       억제 주사는 몇 시에 맞으라고 했나요?
       [과배란 주사와 같이] [아침] [시간 따로 들었어요]
나     [과배란 주사와 같이]
Fevio  토요일 진료 시각은요?   [09:00] [09:30] [10:00] [모르겠어요]
나     [모르겠어요]
Fevio  비워 둘게요. 병원 문자 오면 붙여 주세요
       [이대로 확정] [직접 고치기]
```

- 모델의 일: 말·사진·텍스트에서 처방 변경을 **현재 처방 목록과 맞춰** 뽑기, 빈칸만 골라 되묻기.
- 되묻기는 **정해진 질문 목록**에서 고른다(시각, 날짜, 단위, 시작일, 종료 조건). 모델이 새 질문을 만들지 않는다.
- 단위가 등록된 약과 다르면(예: 'IU'가 아니라 '개') 확정 전에 반드시 되묻는다. 단위 혼동이 가장 흔한 오류이기 때문이다 **[근거: 용량·단위 혼동 20.5%]**.
- "모르겠어요"는 정상 답이다. 빈칸으로 두고 실행 카드로 만들지 않는다.

### B. 투약 확인

시작 조건: 투약 묶음 정시 알림을 눌러 들어옴.

```text
Fevio  21:00 주사 3개예요. 다 맞았나요?
       [모두 맞았어요] [하나씩 체크] [못 맞은 게 있어요]
나     [못 맞은 게 있어요]
Fevio  어떤 거예요?  [과배란 주사A] [과배란 주사B] [억제 주사]
나     [억제 주사]
Fevio  기록해 둘게요. 놓친 주사는 병원 안내를 따라야 해요
       ┌ 병원 연락 ───────────────┐
       │ OO병원 난임센터  02-xxx-xxxx │
       │ 지금 운영 중 · 19:00까지      │  ← 병원이 입력한 운영 시간
       └─────────────────────────┘
       [병원에 메시지 남기기] [전화하기]
```

- 놓친 투약에 대해 앱은 **어떻게 하라고 말하지 않는다**. 병원 연락 경로만 보여준다.
- 병원이 연결된 경우 '병원에 메시지 남기기'는 맥락(약, 예정 시각, 지금 시각, 단계)이 붙은 문의로 들어간다.

### C. 진료 전 인터뷰 (병원 설정)

시작 조건: 진료 전날 저녁. 질문 목록은 병원이 정한다.

```text
Fevio  내일 09:30 진료 전에 세 가지만 물어볼게요. 1분이면 돼요
       지난 사흘, 배가 불러서 불편한 정도는요?
       [거의 없음] [조금] [꽤] [많이]
나     [조금]
Fevio  소변 양이 평소보다 줄었나요?  [아니요] [조금] [많이]
나     [아니요]
Fevio  진료실에서 물어보고 싶은 게 있나요?
       [없어요] [있어요 · 말로] [있어요 · 적기]
나     (말로) 채취 날짜 언제쯤인지
Fevio  정리했어요. 병원에 미리 보낼까요?
       ┌ 진료 전 정리 ──────────────┐
       │ 투약  지난 3일 9/9 정시      │
       │ 불편  배부름 조금 · 소변 정상 │
       │ 질문  채취 날짜              │
       └──────────────────────────┘
       [병원에 보내기] [나만 보기]
```

- 질문, 선택지, 경고 기준은 **병원이 정한다**. 예를 들어 과자극 증후군(OHSS) 경고 증상은 병원마다 기준과 연락 경로가 다르다 **[근거: 병원별 안내문]**.
- 경고 기준에 걸리면 **규칙이** 연락 카드를 띄운다. 예: 소변 '많이 줄었어요', 숨이 참, 심한 복통. 모델은 위험도를 판단하지 않는다.
- 운영 시간 밖이면 병원이 정한 야간 안내(당직 번호, 응급실)를 그대로 보여준다.

### D. 질문하기

```text
나     트리거 맞고 샤워해도 돼요?
Fevio  병원 안내문에 이렇게 있어요
       "…" — OO병원 채취 안내문 2쪽
       [이해했어요] [더 물어볼래요 → 코디네이터에게]
```

- 답은 **병원이 승인한 자료**(안내문, 자주 묻는 질문)에서만 가져오고 출처를 붙인다.
- 자료에 없으면 답하지 않고 코디네이터 문의로 넘긴다. 그때 지금 단계, 최근 투약, 질문 원문이 함께 간다.
- 병원이 연결되지 않은 경우 일반 사실(예: 약 보관 온도)은 허가 사용설명서 출처일 때만 답한다.

### E. 이해 확인 (처방이 바뀐 뒤)

```text
Fevio  바뀐 걸 한 번만 같이 확인해요
       내일 억제 주사는 언제 맞아요?
       [21:00 과배란 주사랑 같이] [아침 9시] [모르겠어요]
나     [21:00 과배란 주사랑 같이]
Fevio  맞아요. 둘 다 21:00 묶음에 넣어 뒀어요
```

- 바뀐 처방을 환자가 스스로 말하게 해서 이해를 확인하는 방식(teach-back)이다. 이해도를 높인다는 근거는 비교적 일관되고, 복약 순응에 대한 효과는 연구마다 엇갈린다 **[근거: teach-back 체계적 문헌고찰]**.
- 틀리면 고쳐 주고, 병원 연결 시 '이해 확인 실패'가 기록되어 코디네이터가 볼 수 있다.

## 3. 커튼 화면 구성 (컴포넌트 단위)

### 3-1. 높이 상태

| 상태 | 높이 | 언제 | 아래 화면 |
|---|---|---|---|
| 엿보기 | 화면의 약 45% | 첫마디와 칩 답변 | 밀려나되 다이얼 일부가 보임 |
| 펼침 | 전체 | 키보드 입력, 사진 확인, 긴 정리 | 가려짐 |
| 닫힘 | 0 | 위로 밀어 올리거나 '나중에' | 원래대로 |

- 칩 답변은 엿보기 상태에서 끝난다. 사용자가 입력칸을 누르면 그때 펼침으로 바뀌고, 키보드 위에 입력줄이 붙는다.
- 펼침 상태에서 키보드가 올라와도 '정리 중' 칸과 마지막 메시지 두 개는 보이도록 배치한다.
- 닫았다 다시 열면 이어서 시작한다. 확정되지 않은 정리는 초안으로 남고, 홈에 '정리 중 1건'으로 표시된다.

### 3-2. 요소

| 요소 | 역할 | 규칙 |
|---|---|---|
| 정리 중 칸 (상단 고정) | 대화가 만드는 구조화 결과 | 항목마다 태그(용량·추가·중단·진료·금식). 빈칸은 '?'로 표시 |
| Fevio 메시지 | 짧은 질문·확인 | 한 번에 한 질문, 두 줄 이내 |
| 선택지 칩 | 기본 답변 방식 | 2~4개, '모르겠어요' 항상 포함 |
| 음성 버튼 | 진료 직후, 한 손 | 받아쓴 글을 메시지로 보여주고 고칠 수 있게 |
| 사진 버튼 | 스케줄표·약 봉투 | 인식 결과는 정리 중 칸으로만 들어감 |
| 출처 카드 | 병원 승인 자료 인용 | 문서명·쪽 표시, 원문 보기 |
| 연락 카드 | 병원 연결 | 운영 시간, 전화, 메시지 |
| 확정 바 | 마지막 단계 | [이대로 확정] [직접 고치기] |

### 3-3. 대화 예산

- 진료 뒤 정리는 **4턴 이내**를 목표로 한다. 넘으면 '직접 고치기'를 먼저 제안한다.
- 한 턴에 두 가지를 묻지 않는다.

## 4. 모델이 하는 일과 하지 않는 일

| 할 수 있음 | 하지 않음 (CLAUDE.md, north star 근거) |
|---|---|
| 말·사진·텍스트에서 처방 변경 추출 → 정해진 형식 | 용량을 추론하거나 맞는지 판단 |
| 빈칸에 맞는 질문을 정해진 목록에서 고르기 | 새 의료 질문 만들기 |
| 병원 승인 자료를 찾아 인용 | 자료 밖 의학적 답변 |
| 답을 모아 진료 전 정리 만들기 | 증상 위험도 판단, 진단 |
| 문의를 요약해 코디네이터에게 넘기기 | 역할 지정, 우선순위 결정 |
| 짧고 절제된 말투로 묻기 | 위로·격려 과잉, 결과 예측 |

결정론적 층(모델 밖):

- 형식 검사: 시각, 날짜, 단위가 등록된 약과 맞는지
- 위험 신호 규칙: 병원이 정한 기준표
- 운영 시간과 연락 경로
- 확정: 사용자 버튼만

실패 시: 모델 응답이 형식 검사를 통과하지 못하거나 시간이 초과되면, 그 항목을 빈칸으로 두고 수동 입력으로 넘긴다(fail closed).

## 5. 구조

```text
커튼 UI ──▶ 대화 조정기 (상태 기계: A~E)
               ├─ extract_regimen_diff(text | image | audio_transcript) → RegimenDiff 초안
               ├─ next_clarification(diff) → 정해진 질문 ID (빈칸 기준)
               ├─ search_clinic_content(query) → 승인 자료 조각 + 출처
               ├─ evaluate_alert_rules(answers) → 결정론적 규칙 (모델 아님)
               ├─ create_clinic_ticket(summary, context) → 병원 대기열
               └─ commit(diff) → 사용자 확정 시에만 Regimen / DoseEvent / CycleEvent
```

- 대화 기록과 정리 중 칸은 **같은 초안 객체**를 본다. 대화로 고치든 '직접 고치기'로 고치든 결과는 같다.
- 확정 시 처방·투약·단계 사건이 함께 만들어진다(`care-input-and-dosing-flow.md` §5-1, `src/domain/cycle-state-machine.ts`).
- 모델 키는 서버(Vault)에만 둔다(CLAUDE.md).

## 6. 병원이 모델까지 연결했을 때 얻는 것

| 병원이 얻는 것 | 어떻게 | 병원 지표 |
|---|---|---|
| 진료 전 정리된 환자 보고 | C 인터뷰 결과가 진료 전에 도착 (투약 수행, 불편 증상, 질문) | 진료 중 확인 질문에 쓰는 시간 |
| 반복 문의 감소 | D가 승인 자료로 답, 못 하는 것만 넘김 | 자동 해결률, 주기당 전화 수 |
| 맥락 붙은 문의 | 넘어오는 문의에 단계, 최근 투약, 원문이 붙음 | 코디네이터 첫 답변까지 시간 |
| 처방 이해 확인 기록 | E 결과와 확인 시각 | 이해 확인 실패율, 실패 후 연락 |
| 위험 신호 연결 | 병원 기준표로 연락 카드, 기록 남김 | 경고 발생 → 병원 연락까지 시간 |
| 처방 전달 | 코디네이터가 보낸 변경을 A 대화로 확인 | 변경 확인률, 확인까지 시간 |

- **[가설]** 코디네이터 업무의 상당 부분은 같은 질문 반복과 처방 재설명이다. 인터뷰로 확인해야 한다. 국내 코디네이터 업무량 자료는 아직 찾지 못했다.
- **[가설]** 진료 전 정리가 진료 시간을 줄이는지는 시범 병원에서 측정해야 한다.

### 병원 콘솔 (최소)

- **문의함:** 넘어온 질문을 맥락과 함께 보고, 답하면 환자 커튼에 이어서 표시
- **진료 전 정리:** 내일 진료 환자별 요약
- **처방 보내기:** 템플릿에서 바뀐 것만 고쳐 전송
- **자료 관리:** 안내문, 자주 묻는 질문 (답변 근거)
- **규칙 관리:** 진료 전 질문 목록, 경고 기준, 운영 시간, 야간 안내

---

## 7. 위험과 조건

- **민감정보:** 처방·증상 대화가 모델로 간다. 별도 동의, 처리 위탁 계약, 국외 이전 여부, 보관 기간을 정해야 한다 **[결정 필요]**.
- **의료기기 해당 여부:** 병원 승인 자료 인용, 규칙 기반 경고, 진료 전 질문은 의료기기 소프트웨어 판단에 영향을 준다. 식약처 기준 검토가 필요하다 **[결정 필요]**.
- **환각:** 형식 검사, 정해진 질문 목록, 출처 없는 답 금지, 확정은 사용자만 하는 구조로 막는다.
- **과신:** 앱이 답해 주면 병원에 연락하지 않을 수 있다. 위험 신호와 놓친 투약은 항상 병원 연락 카드로 끝낸다.
- **운영 시간 밖:** 병원이 정한 야간 안내만 보여준다. 앱이 판단해 '괜찮다'고 말하지 않는다.
- **말투:** north star의 절제된 따뜻함을 따른다. 과한 위로, 결과 예측, 탓하는 말을 쓰지 않는다.

## 8. 지표

| 지표 | 목표/의미 |
|---|---|
| 진료 뒤 정리 완료율 | 진료 후 24시간 안에 확정된 비율 |
| 평균 턴 수 | 4턴 이내 |
| 추출 정확도 | 확정 시 사용자가 고친 항목 비율 (낮을수록 좋음) |
| '모르겠어요' 비율 | 높으면 병원 전달 방식 문제 신호 |
| 자동 해결률 (D) | 병원 승인 자료로 끝난 질문 비율 |
| 이해 확인 실패율 (E) | 처방 변경 뒤 오답 비율 |
| 진료 전 인터뷰 응답률 (C) | 병원 연결 시 |

## 9. 다음 단계

1. 시안: 커튼 대화 A(진료 뒤 정리)와 B(투약 확인)를 엿보기/펼침 상태로 그리기. 정리 중 칸이 채워지는 동작 포함.
2. 계약 정의: `RegimenDiff` 형식, 되묻기 질문 목록, 경고 규칙 형식, 병원 문의 형식.
3. 모델 없이 동작하는 버전 먼저: 정해진 질문 목록과 규칙만으로 A~E를 돌리는 결정론적 대화. 모델은 추출과 자료 검색에만 붙인다.
4. 병원 인터뷰: 반복 문의 유형, 진료 전 알고 싶은 것, 경고 기준과 야간 안내 방식.
