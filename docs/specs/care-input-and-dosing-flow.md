## 0. 요약

1. Fevio가 다루는 문제의 본질은 "일정"이 아니라 **2~3일마다 바뀌는 처방을 매일 여러 번, 정확히 실행하는 것**이다. 그래서 입력과 화면의 1급 시민은 '일정'이 아니라 **처방 변경(diff)과 투약 묶음(dose bundle)**이어야 한다.
2. 실제 사용자는 자유 텍스트를 거의 쓰지 않는다. 정보는 종이 스케줄표, 약국 봉투 라벨, 코디네이터 카톡/문자, 진료실 구두 안내로 들어온다. 입력은 **"어제 계획 + 오늘 바뀐 것"**을 탭으로 고치는 방식이 기본이어야 하고, 키보드는 마지막 수단이다.
3. 커튼(위에서 내려와 화면을 미는 패널)은 입력용으로 맞지 않는다. 키보드가 올라오면 남는 공간이 거의 없다. 커튼은 **'오늘 전체 투약표를 당겨 보는' 읽기 전용 도구**로 축소하고, 입력은 전체 화면 흐름으로 옮긴다.
4. 홈의 반원은 '주사 하나'가 아니라 **하루 투약 전체를 한 바퀴에 놓는 다이얼**이어야 한다. 하루 2~4번의 투약 시점이 다이얼 위에 있고, 다음 묶음까지 남은 시간이 가운데에 온다.
5. 병원이 이 앱을 환자에게 주는 이유는 "환자 편의"가 아니라 **병원의 안내 업무와 투약 오류 비용을 줄이는 채널**이기 때문이다. 병원이 제공하는 버전에서는 **코디네이터가 처방 일정을 보내고 환자가 확인**하는 것이 가장 좋은 입력이 된다.
6. 역할 분담(누가 무엇을 맡는다)은 화면에서 뺀다. 둘이 같은 일정을 보고, 한 사람이 체크하면 다른 사람에게 보이는 것으로 충분하다. 기록은 내부적으로 `administered_by / recorded_by / confirmed_by`를 분리해 유지한다(north star §9).

## 1. 이 버티컬에서 왜 이 앱이 쓰여야 하나

### 1-1. 체외수정 한 주기의 실제 운영 구조

```text
생리 시작 ─ 진료(초음파·피검사) ─ 과배란 주사 시작
   └ 2~3일마다 진료 → 용량 조정 / 약 추가(억제 주사 등) / 다음 진료일 결정
        └ 트리거 주사 (정해진 시각) → 약 34~36시간 뒤 채취 (시각은 병원이 정함)
             └ 배양 → 이식 → 황체기 보조(질정·경구·주사 등 하루 여러 번) → 판정
```

- **[근거]** 진료 시간이 하루 이틀 전에야 정해지는 경우가 많아 일정 조율이 어렵다 (해외 코디네이터 자료).
- **[가설 · 확인 필요]** 하루 투약 횟수는 단계와 프로토콜마다 다르다. 과배란 기간에는 저녁 주사 1~3종에 경구약이 더해지고, 이식 뒤에는 질정·경구약이 하루 2~3회로 늘어나는 경우가 흔하다. 실제 분포는 협력 병원의 프로토콜 표 2~3개로 확인한다.

즉 사용자가 관리하는 건 "날짜 몇 개"가 아니라 다음 세 가지다.

| 무엇 | 빈도 | 바뀌는 주기 |
|---|---|---|
| 투약 (약 × 용량 × 시각) | 하루 2~6회 | 진료마다 (2~3일) |
| 진료 (날짜·시각·준비물·금식) | 2~3일마다 | 진료 당일 결정 |
| 단계 전환 (트리거, 채취, 이식, 판정) | 주기당 4~5번 | 진료에서 결정 |

### 1-2. 어디서 실패하나

| 실패 지점 | 근거 | 결과 |
|---|---|---|
| 용량·단위 혼동 | **[근거]** 프랑스 28개 센터 연구: 두 번째 방문 시 27%가 투약 일정·용량 미준수 또는 혼란을 보고, 의사-환자 기록 불일치 20.5%(주로 단위·용량 혼동) | 과소/과다 투여 |
| 펜 사용 오류 | **[근거]** 다회용 펜에서 첫 사용 준비(프라이밍) 누락, 용량 창 확인 누락이 가장 흔한 치명적 오류. 새 펜으로 이어 맞는 상황도 오류 원인 | 실제 투여량 불명확 |
| 트리거 시각 | **[근거]** 트리거 실패 시 난자가 나오지 않는 경우가 보고됨(드묾, 대부분 증례 수준) | 주기 실패 |
| 정보 전달 누락 | **[근거]** 원 기획 노트 인터뷰 B: 아내가 듣고 남편에게 전달하는 과정에서 누락·왜곡 | 실수, 갈등 |
| 치료 중단 | **[근거]** 중단 이유 중 신체·심리 부담 약 19% (Gameiro 2012) | 누적 성공 기회 상실 |

### 1-3. 지금 쓰는 도구의 한계

| 지금 쓰는 것 | 못 하는 것 |
|---|---|
| 종이 스케줄표 | 용량이 바뀌면 줄 긋고 다시 씀. 남편과 공유 안 됨. 알림 없음 |
| 카톡/문자 안내 | 과거 메시지에 묻힘. 일정으로 바뀌지 않음 |
| 휴대폰 알람 / 캘린더 | 반복 일정이 바뀔 때마다 직접 고쳐야 함. 약별 용량 표시 못 함. 기록이 진료로 돌아가지 않음 |
| 일반 복약 앱 | 2~3일마다 바뀌는 처방, 트리거·채취 같은 단계, 펜 사용을 다루지 못함 |

### 1-4. Fevio의 자리

> **바뀌는 처방을, 하루 여러 번, 둘이 같이 정확히 실행하게 하고, 그 기록을 다음 진료로 돌려보낸다.**

이 문장에서 빠지면 안 되는 것:

- '바뀌는' → 변경이 입력의 기본 단위
- '하루 여러 번' → 투약 묶음과 하루 다이얼
- '둘이 같이' → 같은 일정 공유와 알림 (역할 지정이 아님)
- '진료로 돌려보낸다' → 진료 브리핑 (병원 가치의 핵심)

## 2. 병원이 이 앱을 제공해야 하는 이유

### 2-1. 환경

- **[근거]** 2024년부터 난임 시술비 지원의 소득기준이 전국적으로 폐지되었고, 체외수정은 신선·동결 구분 없이 총 20회까지 지원된다(지자체 기준 최대 25회).
- **[가설]** 지원 확대로 환자 수와 회차가 늘어, 코디네이터·간호 인력의 안내·문의 업무가 함께 늘었을 가능성이 크다. 국내 코디네이터 업무량 자료는 이번 조사에서 찾지 못했다. 병원 인터뷰로 확인이 필요하다.

### 2-2. 병원이 얻는 것

| 병원 가치 | 어떻게 | 병원이 볼 지표 |
|---|---|---|
| 반복 문의 감소 | 바뀐 처방이 환자 앱에 구조화되어 도착하고, 환자는 앱에서 확인 | 주기당 전화·카톡 문의 수 |
| 안내 기록 | 환자가 확인한 시각이 남음 ("안내했고 환자가 확인함") | 처방 변경 확인률, 확인까지 걸린 시간 |
| 투약 오류로 인한 주기 손실 감소 | 용량·단위 확인, 펜 안내, 트리거 이중 확인 | 투약 관련 취소·재조정 건수 |
| 진료 시간 단축 | 진료 전 브리핑: 지난 기간 정시 수행, 지연, 증상, 질문 | 진료당 '확인 질문'에 쓰는 시간 (자기 보고) |
| 환자 유지 | 운영 부담 감소 → 다음 주기 지속 | 다음 주기 진행률 |

### 2-3. 병원 제공 버전에서 바뀌는 입력

가장 정확한 입력은 환자가 아니라 **병원이 보내는 처방 일정**이다.

```text
코디네이터 콘솔(웹) 또는 EMR 내보내기
  → 처방 일정 전송 (약, 용량+단위, 시각, 기간, 다음 진료, 금식 등)
  → 환자 앱: "병원에서 일정이 바뀌었어요" 알림
  → 환자가 바뀐 점을 보고 '확인' (확정은 여전히 환자)
  → 병원 콘솔에 확인 시각 기록
```

- 환자 쪽 사진·탭 입력은 **협력하지 않는 병원 환자용 대체 경로**가 된다.
- 콘솔은 EMR 연동 없이도 시작할 수 있다. 코디네이터가 템플릿(프로토콜별 기본값)에서 바뀐 것만 고치게 한다.
- **[결정 필요]** 이렇게 하면 앱이 처방 전달 경로가 되므로 의료법·의료기기 해당 여부 검토가 먼저다. 원 기획 노트의 미결 질문 1과 같은 항목이다.

### 2-4. 검증 계획

- 병원 2~3곳의 코디네이터 인터뷰: 주기당 문의 수, 가장 많은 문의 유형, 처방 변경 전달 방식(종이/카톡/전화).
- 병원 1곳과 4주 시범: 콘솔에서 보낸 변경 → 환자 확인률, 문의 수 변화.

## 3. 입력 — 실제 사용자는 어떻게 넣나

### 3-1. 정보가 들어오는 곳

| 원천 | 형태 | 순간 | 지금 앱 | 제안 |
|---|---|---|---|---|
| 진료실 구두 안내 | 말 | 진료 직후, 대기실·주차장, 한 손 | 붙여넣기 칸 | **바뀐 점 탭 입력** + 음성 메모(나중에 정리) |
| 종이 스케줄표 | 표(손글씨 포함) | 진료 직후 / 집 | 사진 탭(가짜) | **사진 → 표 인식 → 확인표** |
| 약국 봉투·약 상자 | 라벨(약 이름, 용법) | 약 받은 직후 | 없음 | **약 등록: 라벨 사진 → 약 이름·형태 인식** |
| 코디네이터 카톡/문자 | 짧은 텍스트 | 아무 때나 (진료 다음 날 결과 연락 등) | 붙여넣기 | 복사 → 앱 열면 클립보드 감지 제안. iOS 웹앱은 '공유하기'로 받을 수 없음 **[근거]** |
| 병원 전송 | 구조화 데이터 | 진료 직후 | 없음 | **받기 → 확인** (병원 제공 버전) |

### 3-2. 입력의 본질은 '변경'이다

첫 진료 이후 대부분의 입력은 아래 다섯 중 하나다.

```text
그대로        (어제 처방 유지, 다음 진료일만 바뀜)
용량 변경     (같은 약, 용량만)
약 추가       (예: 억제 주사 시작)
약 중단       (예: 과배란 주사 오늘이 마지막)
단계 일정     (트리거 시각, 채취일, 이식일, 금식)
```

그래서 기본 입력 화면은 빈 칸이 아니라 **지금 처방 목록이 미리 채워진 화면**이다.

```text
진료 끝 · 무엇이 바뀌었나요?
┌───────────────────────────────┐
│ 과배란 주사A   225 IU  21:00   [그대로 ▾] │
│ 과배란 주사B    75 IU  21:00   [그대로 ▾] │
│ 억제 주사       1개    21:00   [그대로 ▾] │
│ + 약 추가                             │
├───────────────────────────────┤
│ 다음 진료   [토 11.23 ▾] [09:30 ▾]      │
│ 트리거·채취  [아직 없음 ▾]              │
└───────────────────────────────┘
[사진으로 확인]            [저장 · 바뀐 점 2개]
```

- 각 줄의 [그대로 ▾]는 `그대로 / 용량 / 시각 / 중단`을 고르는 메뉴. 용량은 키보드 대신 **스테퍼와 단위 고정 칩**으로 고친다(단위 혼동이 핵심 오류이므로 단위는 약 등록 때 고정).
- 저장하면 '바뀐 점' 요약을 보여주고 확정한다. 확정 전 항목은 실행 카드가 되지 않는다(CLAUDE.md 확인 우선 원칙).
- 처음 한 번은 약 등록이 필요하다: 약 이름(라벨 사진 인식 또는 목록 검색), 형태(펜/바이알+희석/프리필드/질정/경구), 단위, 보관.

### 3-3. 키보드를 피한다

| 값 | 입력 방식 |
|---|---|
| 용량 | 스테퍼(병원이 쓰는 증감 단위, 예: 25/37.5/75) + 고정 단위 |
| 시각 | 자주 쓰는 시각 칩(21:00, 22:00) + 휠 |
| 날짜 | 주간 띠에서 탭 |
| 약 이름 | 사진 인식 또는 목록 검색 (첫 등록 때만) |
| 메모 | 음성 우선, 텍스트는 선택 |

### 3-4. 입력 경로 우선순위

1. 병원이 보낸 일정 받기 (병원 제공 버전)
2. 바뀐 점 탭 입력 (기본)
3. 사진 → 확인표 (첫 처방, 스케줄표가 바뀐 날)
4. 음성 메모 → 나중에 정리 (진료 직후 시간이 없을 때)
5. 텍스트 붙여넣기 (카톡 안내 등)

지금 시안의 `붙여넣기 | 사진` 탭은 5번과 3번만 있고, 가장 자주 쓰일 2번이 없다.

## 4. 커튼에 대한 결론

> 갱신(2026-11-19): 커튼을 모델이 연결된 대화 계면으로 다시 정의했다. 이 장의 결론은 '자유 텍스트 입력 칸으로서의 커튼'에 대한 것이며, 커튼의 역할은 `docs/specs/agent-interaction-layer.md`가 대체한다.

- **문제:** 커튼이 화면을 560pt 밀어내고, 그 위에서 텍스트 입력을 하면 한글 키보드(대략 화면 아래 40%)가 커튼 아래쪽 버튼과 입력칸을 가린다. 밀려난 원래 화면은 보이지 않는다. 결과적으로 입력에도 확인에도 공간이 부족하다.
- **결론:** 커튼은 입력 도구에서 뺀다.
- **남길 가치:** "당겨 내리면 오늘 전체 투약표가 펼쳐지는" 읽기 전용 동작은 홈의 다이얼과 잘 맞는다(엄지로 당기고 놓으면 닫힘, 키보드 없음).
- **입력:** 홈 위 + → 전체 화면 '진료 기록' 흐름(3-2의 화면)으로 이동. 단계: 바뀐 점 → 확인 → 저장. 뒤로가기로 언제든 취소.

## 5. 하루 여러 번 투약 — 모델과 화면

### 5-1. 데이터 모델 (Supabase 대응 초안)

```ts
type Medication = {          // 약 등록 (주기당 1회)
  id: string; name: string;  // 라벨/처방 사진에서 사용자가 확인한 이름
  form: 'pen_multi' | 'pen_single' | 'vial_mix' | 'prefilled' | 'vaginal' | 'oral';
  unit: 'IU' | 'mcg' | 'mg' | '개' | '정';      // 등록 때 고정
  storage: 'fridge' | 'room' | null;            // 허가 사용설명서 출처일 때만 자동
  penCapacity?: number;                         // 다회용 펜 총량 (남은 양 계산용)
};

type Regimen = {             // 처방 한 줄 (바뀌면 새 버전)
  id: string; medicationId: string;
  dose: number; times: string[];                // 하루 여러 시각 가능
  startDate: string;
  end: { kind: 'date'; date: string } | { kind: 'until_next_visit' } | { kind: 'single' };
  source: 'clinic_push' | 'photo' | 'manual';
  confirmedAt: string | null;                   // 확정 전엔 실행 카드 아님
  supersedes?: string;                          // 이전 버전 (바뀐 점 계산)
};

type DoseEvent = {           // 매일 펼쳐지는 실제 투약
  regimenId: string; scheduledAt: string;       // Asia/Seoul 기준 저장
  status: 'upcoming' | 'done' | 'needs_recheck' | 'skipped_by_instruction';
  doneAt?: string; administeredBy?: 'self' | 'partner' | 'clinic';
  recordedBy: string; confirmedByPatient: boolean;
};

type Visit = { date: string; time?: string; fasting?: { from: string }; companionRequired?: boolean };
```

- `Regimen` 확정 시 단계 사건을 함께 만든다: 첫 과배란 확정 → `stimulation_started`, 트리거 확정 → `trigger_scheduled` (`src/domain/cycle-state-machine.ts`와 연결).
- '배란 유도 n일째' = `stimulation_started` 날짜로부터 한국 시간 기준 일수 + 1.
- **레포에서 먼저 고칠 것:** `src/domain/protocol-draft.ts`가 시각을 UTC로 저장한다("밤 10시" → 22:00Z = 한국 시간 다음 날 07:00). 테스트도 이 값을 기대하고 있다(`tests/unit/protocol-draft.test.ts`).

### 5-2. 투약 묶음

같은 시각(±설정 범위)의 투약은 한 묶음으로 보여준다.

```text
21:00 묶음
  ○ 과배란 주사A  225 IU  · 펜 (새 펜 · 첫 준비 필요)
  ○ 과배란 주사B   75 IU  · 바이알 희석
  ○ 억제 주사      1개    · 프리필드
[모두 맞았어요]            ← 하나씩 체크도 가능
```

- 약마다 체크가 따로 있어야 한다. 펜이 다르고, 하나만 빠뜨리는 실수가 가능하기 때문이다.
- 첫 사용 펜, 희석이 필요한 약, 펜을 바꿔 이어 맞는 날에는 그 줄에 **준비 단계 보기**가 붙는다. 출처는 허가 사용설명서다.
- 시간 허용 범위는 앱이 정하지 않는다. 병원이 정하거나 사용자가 병원 안내대로 입력한다. 트리거는 기본 '정각'.

### 5-3. 홈 다이얼 (반원 → 하루 다이얼)

```text
            08:00 ●                 ← 경구약 (끝남, 채움)
       ●                    ○ 21:00 ← 주사 묶음 3개 (다음)
   지금 18:12
            2시간 48분 뒤
            주사 3개
```

- 하루 24시간을 한 바퀴(또는 깨어 있는 시간 반원)에 놓고 투약 시점을 점으로 표시한다. 끝난 건 채우고, 다음 것을 크게 보여준다.
- 가운데: 다음 묶음까지 남은 시간과 묶음 개수.
- 다이얼 아래: 다음 묶음의 약 목록(5-2)과 버튼 하나.
- 당겨 내리면(4장의 커튼) 오늘 전체 투약표가 펼쳐진다.
- **[근거]** 기준서(benchmark 04, 09)의 "주사일은 링/시간이 주인공, 첫 화면 버튼은 하나"를 하루 여러 번 투약으로 확장한 형태다.

### 5-4. 알림과 재확인

| 시점 | 내용 | 대상 |
|---|---|---|
| 묶음 30분 전 | 묶음 약 목록, 냉장 보관 약 꺼내기 | 환자 (+ 공유 상대 선택 시) |
| 정시 | "지금 맞을 시간 · 3개" | 환자 |
| +15분 미확인 | "아직 확인 안 됐어요" (ADR 0006 문구) | 환자 |
| +30분 미확인 | 공유 상대에게 알림 (원 기획 노트 §5-6) | 공유 상대 |

- **[근거]** iOS 웹앱은 홈 화면에 추가해야 웹 푸시를 받을 수 있고, 다른 앱의 '공유하기'로 데이터를 받을 수 없다. 알림이 핵심 가치이므로 **[결정 필요]** 네이티브 앱(또는 웹앱을 감싼 앱)으로 갈지 정해야 한다.

### 5-5. 남은 약 계산 (실제로 쓸모 있는 것)

- 다회용 펜 총량과 확정 용량으로 남은 양을 계산한다. 예: 900 IU 펜, 하루 225 IU → 4일.
- 다음 진료일 전에 떨어지면 미리 알린다: "과배란 주사A가 금요일 밤에 떨어져요 · 다음 진료는 토요일".
- 단순 산수이고 의료 판단이 아니다. 다만 펜의 실제 잔량은 프라이밍 등으로 달라질 수 있으므로 '예상'으로 표시하고, 사용자가 남은 양을 고칠 수 있게 한다.

## 6. 컴포넌트 점검

| 컴포넌트 | 하는 일 | 필요한 데이터 | 실제 사용 가능성 | 위험 / 조건 |
|---|---|---|---|---|
| 하루 다이얼 | 오늘 투약 시점과 다음 묶음까지 남은 시간 | DoseEvent[] (오늘) | 높음. 3초 안에 "다음은 언제, 몇 개" | 투약이 하루 1회면 단순해짐 → 그래도 같은 컴포넌트 |
| 투약 묶음 카드 | 약별 체크, 용량+단위 크게 | Regimen, Medication | 높음 | 용량은 반드시 사용자 확정값. 단위 고정 |
| 준비 단계 보기 | 첫 펜·희석·펜 교체 날에만 | Medication.form, 펜 사용 이력 | 중간. 콘텐츠 확보가 관건 | 허가 사용설명서 출처 필수. 의료기기 해당 검토 |
| 바뀐 점 입력 | 진료 후 처방 수정 | 현재 Regimen 목록 | 높음. 키보드 거의 없음 | 첫 등록은 별도 흐름 필요 |
| 사진 → 확인표 | 스케줄표·라벨 인식 | 이미지, 인식 결과 | 중간. 손글씨 표는 오류 많음 | 인식 결과는 항상 확인표로, 자동 확정 금지(AI 보조 원칙) |
| 진료 브리핑 | 진료 전 정시 수행·지연·질문 | DoseEvent 이력, 질문 메모 | 높음. 병원 가치의 핵심 | 의료 해석 금지, 사실만 |
| 주간 띠 | 날짜 이동, 날짜별 표시 | 날짜별 DoseEvent·Visit | 높음 | 표시는 점 1~2개로 제한 |
| 당겨 보기(커튼) | 오늘 전체 투약표 | DoseEvent[] | 중간. 보조 동작 | 입력에는 쓰지 않음 |
| 남은 약 | 떨어지기 전 알림 | 펜 총량, 용량, 다음 진료일 | 높음 | '예상' 표기, 사용자 수정 가능 |
| 공유 보기 | 같은 일정, 체크 상태 | 공유 범위 | 높음 | 역할 지정 없음. 민감 정보는 공유 범위 따름 |
| 알림 | 30분 전, 정시, +15, +30 | DoseEvent, 채널 | 웹앱에선 낮음 | 네이티브 결정 필요 |

**뺄 것:** 역할 지정 UI, 달성률 링, 투약일 화면의 광고·쉬어가기, 커튼 안의 텍스트 입력.

## 7. 실제 흐름 세 가지

### A. 진료 직후, 용량이 바뀐 날 (토 10:10, 주차장)

1. 앱 알림: "진료 끝났나요? 바뀐 점을 지금 담아 두세요" (진료 예정 시각 + 40분)
2. 열면 바로 '무엇이 바뀌었나요?' 화면 (현재 처방이 채워져 있음)
3. 과배란 주사A: `그대로 ▾` → `용량` → 스테퍼 225→150 IU
4. 억제 주사: `약 추가` → 등록된 약 목록에서 선택 → 시각 21:00 칩
5. 다음 진료: 주간 띠에서 월요일, 09:00 칩
6. 저장 → '바뀐 점 3개' 요약 → 확정 → 공유 상대에게 "일정이 바뀌었어요" 알림
7. 걸린 시간 목표: 1분 이내, 키보드 0회

### B. 저녁 주사 3개 (목 20:30 ~ 21:05)

1. 20:30 알림: "21:00 주사 3개 · 냉장 약 꺼내기" (공유 상대도 받음)
2. 21:00 알림 → 열면 홈 다이얼이 21:00 묶음을 가리킴
3. 과배란 주사A 줄에 '새 펜 · 첫 준비' 표시 → 준비 단계 보기
4. 셋을 하나씩 체크 또는 '모두 맞았어요'
5. 기록: 21:04, 맞은 사람 선택(기본 본인), 공유 상대에게 보임
6. 미확인이면 21:15 재확인, 21:30 공유 상대 알림

### C. 다음 진료 전에 약이 떨어지는 경우 (수 저녁)

1. 남은 약 계산: 과배란 주사A 펜이 금요일 밤에 떨어짐, 다음 진료 토요일
2. 수요일 저녁 알림: "금요일 밤에 과배란 주사A가 떨어져요 · 병원이나 약국에 미리 확인해 주세요"
3. 화면에서 바로 병원 연락처, 처방 사진 보기

## 8. 기술 · 규제 제약

- **웹앱 한계 [근거]:** iOS에서 웹 푸시는 홈 화면에 추가한 웹앱만 받을 수 있다. 다른 앱의 '공유하기'로 받을 수 없다. 잠금화면 위젯과 실시간 현황(Live Activity)도 쓸 수 없다.
- **알림 결정 기록 갱신 필요:** ADR 0004(이메일만)와 ADR 0006(앱 안 재확인만)은 이 기획의 핵심 가치와 맞지 않는다. 다시 결정해야 한다.
- **사진 인식:** 인식 결과는 항상 확인표로만 나온다. 자동 확정 금지(CLAUDE.md의 AI 보조 원칙).
- **의료기기 · 의료법:** 약 준비 안내, 병원 처방 전송, 남은 약 계산이 의료기기 소프트웨어에 해당하는지 식약처 기준 검토가 필요하다.
- **개인정보:** 처방·투약 기록은 민감정보다. 공유 범위와 병원 콘솔 접근 권한은 RLS 설계(`docs/03-engineering/schema-rls-matrix.md`)에 추가해야 한다.
