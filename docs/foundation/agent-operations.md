# Fevio 운영 설계: 상시 에이전트, 원장(ledger), 개인화된 여정

상태: 설계 초안 · 구현 전
관련 문서: `docs/foundation/fevio-2.md`, `docs/specs/decision-points.md`, `docs/specs/agent-interaction-layer.md`, `docs/specs/together-and-coordinator.md`
캔버스: '운영 흐름' 페이지 `F3Ops.dc.html`

## 0. 결론 먼저

- **개인화는 사람마다 다른 프롬프트에서 나오지 않는다.** 사람마다 다른 원장(기록)에서 나온다. 모든 사용자에게 같은 에이전트와 같은 규칙을 쓰고, 다른 것은 그 사람의 확정된 사실, 그 사람이 다니는 병원의 설정, 그 사람이 고른 선호다.
- **에이전트는 상태를 직접 바꾸지 않는다.** 원장에 '제안'만 쓴다. 사실이 되는 길은 둘뿐이다: 사용자가 확정하거나, 병원이 기록하거나.
- **시간이 중요한 일은 모델 없이 돈다.** 투약 알림, 트리거 정각, 결정점 열고 닫기, 공유 반영은 결정적(deterministic) 코드와 큐가 처리한다. 모델이 멈춰도 오늘 21:00 알림은 울린다.
- **"상시 운용"은 큰 에이전트 하나가 계속 생각하는 것이 아니다.** 이벤트가 오면 깨어나는 좁은 작업자 여러 개다. 1,000명이든 10만 명이든 구조는 같고, 수평으로 늘린다.

## 1. 운영 원칙

1. **원장이 유일한 진실이다.** 화면, 알림, 병원 콘솔, 배우자 화면은 모두 원장에서 계산한 투영(projection)이다.
2. **기록은 지우지 않는다.** 정정도 새 이벤트(`supersedes`)로 남긴다.
3. **사실과 추정을 다른 층에 둔다.** 모델이 읽은 것은 '관찰(observation)', 사람이 확정한 것은 '사실(fact)'이다. 실행 객체(알림, 다이얼, 콘솔 지표)는 사실만 쓴다.
4. **보이는 범위는 쓸 때 정한다.** 이벤트마다 환자·배우자·병원·커뮤니티 가시성을 붙인다. 투영이 그 태그로 거른다. 배우자 투영은 원문을 읽지 않는다.
5. **모든 에이전트 실행은 재현 가능하다.** 입력 이벤트 ID, 설정 버전, 모델·프롬프트 버전, 출력, 사용자 수락 여부를 남긴다.
6. **앱을 안 열었다는 사실로 아무것도 추정하지 않는다.** 미투약, 불안, 이해 부족을 앱 사용 기록으로 판단하지 않는다. 투약 상태는 명시적 기록이나 명시적 '빠졌어요'로만 바뀐다.
7. **실패하면 사람에게 닫힌다(fail closed).** 모델 오류, 낮은 확신, 규칙 충돌은 수동 입력이나 코디네이터로 넘긴다. 절대 추정값으로 채우지 않는다.

## 2. 들어오는 것 (입력 목록)

| 출처 | 통로 | 예 | 원문 보관 | 원장에서 무엇이 되나 |
|---|---|---|---|---|
| 병원 콘솔 | 콘솔 기록 / 병원 시스템 연동 | 처방 변경, 진료 예약, 판독 뒤 결정, 연구실 소식 | 콘솔 기록은 영구 | 사실 (병원 기록) |
| 병원 설정 | 설정 배포 | 프로토콜 템플릿, 경고 규칙, 안내문, 운영 시간, 응답 시간(SLA) | 버전별 영구 | 설정 버전 (원장 밖, 이벤트가 버전을 참조) |
| 환자 | 커튼 대화 (글·음성) | "150으로 줄이래요", "아랫배가 아파요" | 음성은 받아쓰기 확정 뒤 30일, 글은 주기 종료 뒤 정책에 따라 | 관찰 → 확정 시 사실 |
| 환자 | + 사진·문자 붙여넣기 | 처방전, 스케줄표, 병원 문자 | 확정 뒤 30일 (사용자가 남기기를 고르면 보관) | 관찰 → 확정 시 사실 |
| 환자 | 잠금화면 알림 버튼 | 맞았어요 / 10분 뒤 / 빠졌어요 | 없음 (이벤트 자체) | 사실 (투약 기록) |
| 환자 | 설정 | 공유 범위, 결과 보호, 알림 시점, 사는 곳 | 없음 | 선호 사실 |
| 배우자 | 같은 앱 초대 계정 | 확인함, 대신 기록 (허용된 경우) | 없음 | 사실 (기록자 표시) |
| 커뮤니티 | 글·댓글 | 경험담, 질문 | 커뮤니티 정책 | 원장 밖 (별도 저장소). 결정점 방 입장만 투영에서 계산 |
| 시스템 | 타이머 | 투약 창 열림, 응답 시간 초과 | 없음 | 시스템 이벤트 |
| 시스템 | 전달 영수증 | 푸시 전달·표시 결과 | 90일 | 운영 로그 (원장 밖) |
| 공공데이터 | 매일 동기화 | 보조금24 공공서비스 목록 | 버전별 | 지원 카탈로그 (원장 밖) + 사용자별 매칭 결과 |

## 3. 원장 설계

### 3-1. 네 개의 층

```text
받은함(Inbox)        원문: 음성·사진·글. 암호화, 짧게 보관, 모델 입력으로만 쓴다
   ↓ 접수 작업자
관찰(Observation)    모델이나 규칙이 읽은 것. 확신도, 모델 버전, 근거 위치. 실행 객체가 되지 않는다
   ↓ 사용자 확정 또는 병원 기록
사실(Fact)           원장 이벤트. 추가만 한다. 정정은 새 이벤트로
   ↓ 투영 작업자 (결정적)
투영(Projection)     오늘 타임라인, 배우자 화면, 결정 달력, 알림 일정, 지원 매칭, 커뮤니티 방
```

### 3-2. 이벤트 봉투 (모든 사실이 같은 모양)

```ts
type LedgerEvent<T extends EventType = EventType> = {
  eventId: string;            // ULID. 시간순 정렬 가능
  streamId: string;           // cycle:{cycleId} 또는 patient:{patientId}
  seq: number;                // 스트림 안의 순번. 쓰기 경쟁은 낙관적 잠금으로 막는다
  tenantId: string | null;    // 병원. 독립 모드면 null
  type: T;
  schemaVersion: number;
  occurredAt: string;         // 실제로 일어난 시각 (UTC)
  recordedAt: string;         // 원장에 들어온 시각 (UTC)
  actor: { kind: 'patient' | 'partner' | 'staff' | 'system' | 'agent'; id: string };
  source: { channel: 'console' | 'emr' | 'curtain' | 'photo' | 'lockscreen' | 'settings' | 'timer'; ref?: string };
  basis?: { observationId?: string; configVersion?: string; agentRunId?: string };
  confirmation: { by: 'patient' | 'staff' | 'system_rule'; at: string };
  visibility: { patient: true; partner: 'none' | 'flow' | 'flow_doses' | 'lab_numbers'; clinic: boolean };
  causationId?: string;       // 이 이벤트를 일으킨 이벤트
  correlationId?: string;     // 한 흐름(예: 토요일 결정) 전체를 묶는 ID
  supersedes?: string;        // 정정하는 이벤트
  payload: PayloadOf<T>;
};
```

- `agent`가 actor인 이벤트는 사실 층에 들어갈 수 없다. 에이전트는 관찰과 제안만 쓴다. 사실의 `confirmation.by`는 환자, 병원 직원, 또는 결정적 시스템 규칙(타이머)뿐이다.
- 기존 `src/types/cycle-event.types.ts`의 `CycleEvent`는 이 봉투의 `payload` 일부로 들어간다. 지금 있는 `reduceCycleState`는 투영 작업자 하나가 된다.

### 3-3. 이벤트 목록 (첫 버전)

| 묶음 | 이벤트 | 누가 확정 |
|---|---|---|
| 주기 | `cycle_opened`, `phase_confirmed`, `cycle_closed` + 기존 `CycleEvent` 16종 | 환자 / 병원 |
| 처방 | `regimen_version_published` (병원), `regimen_version_confirmed` (환자), `regimen_mismatch_flagged` | 병원 / 환자 / 시스템 규칙 |
| 투약 | `dose_window_opened`, `dose_recorded`, `dose_snoozed`, `dose_missed_reported`, `dose_corrected` | 시스템 / 환자 / 배우자(허용 시) |
| 결정점 | `decision_point_opened`, `decision_result_expected`, `decision_resolved` (갈래, 근거: 임상 / 일정 포함) | 병원 |
| 진료 | `visit_scheduled`, `visit_moved`, `visit_done`, `pre_visit_brief_sent` | 병원 / 환자 |
| 연구실 | `lab_update_published` (수정, 배양 일수, 동결) | 병원 |
| 문의 | `ticket_opened` (증상·질문·수치), `ticket_answered`, `ticket_sla_breached`, `alert_rule_matched` | 환자 / 직원 / 시스템 규칙 |
| 선호 | `share_scope_set`, `result_protection_set`, `notify_offsets_set`, `region_set`, `preference_noted` ("밤 9시 이후 통화 어려움") | 환자 |
| 지원 | `support_status_set` ("통지서 받음" 같은 사용자 입력) | 환자 |

### 3-4. 저장과 투영

- `ledger_events`: 월별 파티션, `(stream_id, seq)` 유일 키.
  - RLS: 환자는 자기 스트림만 읽는다. 병원 직원은 자기 병원 스트림만 읽는다. 배우자는 원장을 직접 읽지 못하고 배우자 투영만 읽는다.
- 쓰기는 **아웃박스 패턴**으로 한다. 이벤트와 `outbox`를 한 트랜잭션에 쓰고, 투영 작업자가 아웃박스를 읽어 투영 테이블을 갱신한다.
- 투영 테이블 (모두 다시 만들 수 있음):
  - `journey_state`
  - `timeline_items`
  - `partner_view`
  - `decision_calendar` (병원별)
  - `notification_schedule`
  - `support_matches`
  - `room_membership`
- 투영 로직을 바꾸면 원장을 처음부터 다시 재생(replay)해 투영을 새로 만든다. 그래서 투영 함수는 순수 함수여야 하고 테스트가 있어야 한다.

## 4. 상시 에이전트 = 좁은 작업자들

| 작업자 | 깨우는 것 | 읽는 것 | 쓰는 것 | 모델 | 실패 시 |
|---|---|---|---|---|---|
| **접수** | 커튼 글·음성·사진 | 받은함 원문, 맥락 묶음 | 관찰, 되묻기 질문 | 받아쓰기, 추출(용량·시각·날짜) | 수동 입력 폼, "제가 잘 못 읽었어요" |
| **대조** | 관찰 확정, 병원 처방 게시 | 환자 확정 처방, 병원 처방 | `regimen_mismatch_flagged` | 없음 (규칙) | — |
| **일정** | 처방 확정, 결정 확정, 선호 변경 | 확정 처방, 알림 선호, 시간대 | 알림 일정, 기기 로컬 알림 동기화, 캘린더 쓰기 | 없음 | 마지막 확정 일정 유지 + 운영 경보 |
| **결정점** | 진료 예약, 판독 기록, 연구실 소식 | 프로토콜 템플릿, 결정점 | 결정점 열기·닫기, 날짜 범위 계산, 환자·배우자 동시 알림 | 없음 | 범위 숨기고 "병원 확인 중" |
| **대화** | 사용자 메시지 | 맥락 묶음, 병원 승인 안내문 검색 | 답 (출처 카드), 문의 생성 제안 | 대화 모델 + 안내문 검색 | 정해진 질문 버튼과 코디네이터 연결만 |
| **증상 분류** | '몸이 불편해요' | 병원 경고 규칙, 지금 단계 | `alert_rule_matched` 또는 문의 생성 | 없음 (규칙 질문 트리). 자유 문장 분류는 보조로만 | 무조건 전화 버튼 + 문의 생성 |
| **코디네이터 보조** | 문의 생성 | 문의, 단계, 최근 투약, 지난 문의 | 요약, 답변 초안 (직원이 보냄) | 요약·초안 | 원문 그대로 표시 |
| **응답 시간 감시** | 타이머 | 문의 상태, 병원 SLA | `ticket_sla_breached` → 환자에게 당직 번호 노출, 병원 관리자 알림 | 없음 | — |
| **지원 매칭** | 매일 밤, 지역·단계 변경 | 공공 카탈로그, 지역, 단계, 회차 | 지원 매칭 결과 (자격 판정 아님) | 카탈로그 정리 시 분류 보조 | 이전 카탈로그 유지, 갱신일 표시 |
| **커뮤니티 보조** | 글 작성 | 글 | 수치 질문 안내, 광고 의심 → 사람 검토 대기열 | 작은 분류 모델 | 사람 검토로 |
| **진료 전 정리** | 진료 하루 전 타이머 | 지난 진료 뒤 투약 기록, 열린 문의 | 정리 초안 (환자가 보낼지 고름) | 요약 | 기록 표만 |

**모델이 하지 않는 일** (코드로 막는다): 용량 결정, 결정점 갈래 선택, 증상 위험도 판정, 지원 자격 판정, 배우자 공유 범위 변경, 사실 이벤트 쓰기.

## 5. 개인화가 1,000명에게 각각 작동하는 방법

### 5-1. 여정 상태 (journey_state, 사람마다 하나)

```ts
type JourneyState = {
  cycleId: string; tenantId: string | null; configVersion: string;
  phase: IvfPhase; dayInPhase: number;
  activeRegimen: { version: number; bundles: DoseBundle[] } | null;
  openDecisionPoints: DecisionPointView[];   // 무엇을 보고, 언제, 누가, 갈래, 범위
  nextFixed: { kind: 'dose' | 'visit' | 'trigger' | 'procedure'; at: string }[];
  preferences: {
    shareScope: 'off' | 'flow' | 'flow_doses'; labNumbersShared: boolean;
    notifyOffsets: number[]; resultProtection: boolean; foldResultPosts: boolean;
    region: string | null; explanationDensity: 'short' | 'detailed';
    noted: { text: string; confirmedAt: string }[];   // 사용자가 확정한 메모만
  };
  openTickets: { id: string; kind: string; slaDueAt: string }[];
  support: { programId: string; status: 'using' | 'check' | 'not_applicable' }[];
};
```

- 화면은 이 상태 하나로 그린다. 오늘 타임라인, 함께 탭, 커튼의 추천 질문(단계별), 커뮤니티 결정점 방이 모두 같은 상태에서 나온다.
- 같은 단계라도 병원마다 다르게 작동하는 건 `configVersion`이 가리키는 병원 설정(프로토콜 템플릿, 경고 규칙, 안내문, 운영 시간) 때문이다. 코드가 아니라 설정이 다르다.

### 5-2. 맥락 묶음 (context pack): 모델에 무엇을 주나

모델 호출마다 원장 전체를 넣지 않는다. 묶음 작성기가 다음만 모은다.

1. `journey_state`에서 필요한 필드. 이름 대신 가명을 쓰고, 생년월일과 연락처는 넣지 않는다.
2. 지금 흐름(`correlationId`)과 관련된 최근 이벤트 최대 N개.
3. 병원 승인 안내문 중 검색된 조각 최대 K개 (조각 ID 포함, 답에 출처로 표시).
4. 사용자가 확정한 선호 메모.
5. 지금 시각과 병원 운영 상태.

토큰 예산은 작업자별로 고정한다(대화 4천, 추출 8천 토큰 수준에서 시작해 평가로 조정). 넘치면 오래된 이벤트부터 뺀다.

**장기 기억은 따로 없다.** 기억은 원장이고, 자유 형식의 대화 요약을 기억으로 쌓지 않는다. 대화에서 나온 선호("밤 9시 이후 통화 어려움")는 사용자가 확정해야 `preference_noted`가 된다.

## 6. 사용자 워크플로우와 원장에 남는 것

### 6-1. 한 주기 전체 (환자 기준)

| 단계 | 사용자가 하는 일 | 시스템이 하는 일 | 대표 이벤트 |
|---|---|---|---|
| 연결 | 병원이 준 초대 코드 입력, 동의, 배우자 초대(선택) | 병원 스트림 연결, 설정 버전 고정, 첫 여정 상태 생성 | `cycle_opened`, `share_scope_set` |
| 자극 | 알림에서 '맞았어요' | 투약 창 열기·닫기, 알림, 펜 남은 양 계산 | `dose_window_opened`, `dose_recorded` |
| 모니터링 | 진료 가기, 결과 듣기 | 결정점 열기, 결과 예상 시각 표시, 결정 나면 동시 알림 | `decision_point_opened`, `decision_resolved` |
| 트리거·채취 | 정각 투약, 금식, 동반 | 트리거 이중 알림, 채취 고정 일정, 캘린더 쓰기 | `regimen_version_published`, `visit_scheduled` |
| 연구실 | 전화 기다리기 | 연구실 소식 반영, 다음 결정점, 지원 항목(신선/동결) 안내 | `lab_update_published` |
| 이식·기다림 | 남은 투약, 판정일 | 결과 보호 선호 반영, 커뮤니티 결과 글 접기 | `result_protection_set` |
| 결과·다음 | 원할 때 기록 | 주기 닫기, 다음 주기 계획 | `cycle_closed` |

### 6-2. 핵심 흐름 다섯 개 (이벤트 순서)

**A. 병원이 판독 뒤 용량을 바꾼다 (병원 연동)**

1. 병원이 콘솔에서 `decision_resolved`(갈래: 하루 더)와 `regimen_version_published`(v3)를 기록한다.
2. 결정점 작업자가 다음 결정점을 연다(`decision_point_opened`: 월 오전). 날짜 범위는 템플릿으로 계산한다.
3. 일정 작업자가 오늘 21:00 알림의 용량을 바꾸고, 기기 로컬 알림을 다시 맞추고, 캘린더 일정을 옮긴다.
4. 환자 알림 "처방이 바뀌었어요 · 확인"이 간다. 환자가 확인하면 `regimen_version_confirmed`가 된다. 21:00 전까지 확인하지 않으면 알림에 바뀐 용량과 '어제와 다름'을 함께 보여 준다.
5. 배우자 투영이 갱신되고 같은 순간에 알림이 간다(공유 범위 안에서만).

**B. 환자가 말로 들은 변경을 전한다 (독립 모드)**

1. 커튼에 "150으로 줄이래요, 토요일 아침에 오래요"라고 말한다.
2. 접수 작업자가 관찰을 만든다: 용량 225→150 IU, 진료 토, 시각 빈칸.
3. 비어 있는 시각과 단위를 되묻는다.
4. 사용자가 확정하면 `regimen_version_confirmed`(source: curtain)와 `visit_scheduled`가 된다. 이후는 A와 같다.
5. 나중에 병원이 연동되면 대조 작업자가 두 처방을 비교한다. 다르면 `regimen_mismatch_flagged`가 병원 콘솔 맨 위에 뜬다.

**C. 밤 11시, 몸이 불편하다**

1. '몸이 불편해요'를 누르면 병원 경고 규칙의 질문 트리를 따라간다.
2. 규칙에 해당하면 `alert_rule_matched`가 되고, 당직 전화 버튼이 맨 위에 온다.
3. 해당하지 않으면 `ticket_opened`가 된다(단계, 최근 투약, 고른 답이 붙음).
4. 응답 시간 감시 작업자가 병원 SLA를 잰다. 넘기면 `ticket_sla_breached`가 되고, 환자에게 당직 번호를 다시 보여 주며 병원 관리자에게 알린다.
5. 직원이 답하면 `ticket_answered`가 된다. 코디네이터 보조가 만든 요약과 초안은 직원 화면에만 있다.

**D. 투약을 빠뜨렸다**

1. 21:00 알림 뒤 기록이 없으면 +15분 재알림이 가고, 배우자에게는 +30분에 간다(설정한 경우).
2. 그래도 기록이 없으면 상태는 '기록 없음'이다. **'놓침'이 아니다.** 앱을 안 열었다는 이유로 미투약을 추정하지 않는다.
3. 환자가 '빠졌어요'를 누르면 `dose_missed_reported`가 되고, 병원 안내(콘텐츠)와 연락 카드로 이어진다. 다음 투약 처리는 병원이 정한다.

**E. 결정이 나면 배우자도 같은 때 안다**

1. `decision_resolved`가 기록된다.
2. 투영 작업자가 환자와 배우자 투영을 한 트랜잭션에서 갱신한다.
3. 같은 `correlationId`로 알림 두 건이 나간다. 환자가 다시 설명할 필요가 없다.

## 7. 1,000명 이상에서의 운영

### 7-1. 부하 가정 (활성 주기 1,000명, 가정이며 시범 데이터로 고친다)

| 일 | 가정 | 하루 건수 | 모델 사용 |
|---|---|---|---|
| 투약 묶음 | 70%가 하루 2묶음 | 약 1,400 | 없음 |
| 알림 | 묶음당 평균 2.4건 (30분 전, 정시, 일부 재알림·배우자) | 약 3,400 | 없음 |
| 커튼 대화 | 35%가 하루 1번, 평균 4턴 | 약 1,400 호출 | 대화 |
| 사진·문자 읽기 | 5% | 약 50 | 추출 |
| 증상·문의 | 2~3% | 20~30 | 없음 (규칙) + 직원용 요약 |
| 커뮤니티 글·댓글 | 글 100, 댓글 500 | 600 | 작은 분류 |
| 지원 매칭 | 매일 밤 1회 | 1,000명 재계산 | 없음 |

- 모델 호출은 하루 약 2,500건이고, 사용자 수에 거의 비례한다(1만 명이면 약 2.5만 건).
- 시간이 중요한 알림은 모델을 쓰지 않는다.
- 몰리는 시간:
  - 20:30~21:30: 투약 알림이 몰린다. 기기 로컬 알림이 1차를 맡고 서버 푸시는 2차다.
  - 오후 2~5시: 결과 전화 뒤 대화가 몰린다.

### 7-2. 실행 구조

- 큐는 Postgres 아웃박스와 작업 큐를 쓴다(예: Supabase Queues 또는 pg-boss). 처음에는 별도 메시지 브로커를 두지 않는다.
- **같은 주기의 작업은 순서대로** 처리한다(파티션 키 = `cycleId`). 다른 주기끼리는 병렬로 처리한다. 모든 작업은 멱등이다(`eventId` 기준 중복 무시).
- 알림 일정은 두 겹이다.
  - 기기 로컬 알림: 확정 처방에서 앞으로 72시간분을 미리 예약한다.
  - 서버 푸시: 보정과 재알림을 맡는다. 기기 쪽 일정과 서버 쪽 일정의 해시를 비교해 어긋나면 다시 맞춘다.
- 트리거는 기기 알림과 서버 알림을 모두 예약한다. 둘 중 하나만 살아 있어도 울린다.

### 7-3. 서비스 목표 (SLO)

| 대상 | 목표 |
|---|---|
| 투약 알림이 예정 시각 ±60초 안에 표시 | 99.9% |
| 병원 결정 → 환자·배우자 화면 반영 | 30초 안에 99% |
| '몸이 불편해요' → 병원 콘솔 표시 | 10초 안에 99.9% |
| 원장 쓰기 확인 전 화면 반영 금지 | 항상 |
| 대화 첫 응답 | 3초 안에 95% (넘으면 "확인하고 있어요" 표시) |

### 7-4. 고장 났을 때

| 고장 | 사용자에게 보이는 것 | 운영 |
|---|---|---|
| 모델 API 장애 | 커튼은 정해진 질문 버튼, 수동 입력, 코디네이터 연결만 | 킬 스위치로 대화 작업자를 정지, 장애 공지 |
| 추출 확신 낮음 | "제가 잘 못 읽었어요"와 빈칸 입력 | 평가 세트에 사례 추가 |
| 병원 시스템 연동 끊김 | 마지막 확정 일정 + "병원 확인 중" 배지 | 병원에 경보, 결정점 범위 숨김 |
| 푸시 전달 실패 | 기기 로컬 알림은 그대로 울림 | 전달률 대시보드, 기기별 재동기화 |
| 응답 시간 초과 | 당직 번호를 다시 보여 줌 | 병원 관리자 알림, 주간 리포트 |

### 7-5. 품질과 평가

- 모든 에이전트 실행을 `agent_runs`에 남긴다: 입력 이벤트, 맥락 묶음 해시, 모델·프롬프트 버전, 출력, **사용자 수락 / 수정 / 거절**.
- 추출 품질은 수락률과 수정 내용으로 본다. 용량·단위 오류 0건이 배포 조건이다.
- 새 프롬프트·모델은 **그림자 모드**(결과를 보여 주지 않고 비교만) → 한 병원에 카나리 배포 → 전체 순서로 내보낸다. 병원별로 켜고 끈다.
- 비용은 '활성 주기당 월 모델 비용'으로 본다. 작업자마다 모델 크기를 고른다: 분류는 작은 모델, 추출과 대화는 평가를 통과한 모델.

### 7-6. 개인정보와 보안

- 모델 입력에는 가명을 쓰고, 이름·연락처·주민번호·주소는 넣지 않는다. 지역은 시군구까지만 넣는다.
- 원문(음성·사진)은 짧게 보관하고, 확정 뒤 지운다. 사용자가 남기기를 고른 경우만 예외다.
- 데이터는 국내 리전에 저장한다. 모델 제공자와는 학습 비사용 계약을 맺는다.
- 배우자, 커뮤니티, 지원 매칭은 원장 원문을 읽지 못한다. 각자의 투영만 읽는다.
- 직원 접근은 역할별로 나누고 감사 기록을 남긴다(누가 어떤 환자 스트림을 열었는지).

## 8. 무엇부터 만드나

1. **원장과 투영의 뼈대.**
   - 이벤트 봉투, `ledger_events` + `outbox` 마이그레이션과 RLS 테스트.
   - 기존 `reduceCycleState`를 투영 작업자로 옮긴다.
   - `journey_state` 투영과 재생 테스트.
2. **일정 작업자.** 확정 처방에서 알림 일정을 만들고 기기 로컬 알림과 동기화한다. 시간대 버그(UTC) 수정이 같이 들어간다.
3. **결정점 작업자와 프로토콜 템플릿 설정.** 배우자 투영 동시 갱신.
4. **문의·증상 흐름과 응답 시간 감시.** 병원 콘솔 문의함.
5. **대화·접수 작업자.** 그림자 모드로 시작하고, 평가 세트를 만든다.
6. **지원 매칭과 커뮤니티 보조.**

1~4는 모델 없이 완성된다. 모델이 멈춰도 제품이 돌아야 한다는 원칙을 순서로도 지킨다.

## 9. 아직 모르는 것

1. 병원 시스템 연동 방식. 국내 난임센터가 쓰는 전자의무기록(EMR)과 연동이 가능한지, 아니면 콘솔 직접 입력이 현실적인지. 입력 부담은 몇 초인지.
2. 결정점 템플릿이 병원마다 얼마나 다른지. 템플릿 몇 개로 대부분을 덮을 수 있는지.
3. 실제 부하 분포. 위 표는 가정이다. 시범 2주 데이터로 고친다.
4. 기기 로컬 알림 72시간 예약이 OS 제한(iOS 예약 알림 개수 등) 안에서 다회 투약과 트리거를 모두 담을 수 있는지.
5. 코디네이터 응답 시간 약속이 병원 인력으로 지켜지는지. 못 지키면 표시를 어떻게 바꿀지.
6. 대화 모델 비용이 활성 주기당 병원 구독 단가 안에 들어오는지.
