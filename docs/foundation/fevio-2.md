# Fevio 2 — 기초 설계 (Foundation)

Status: Proposed (2026-11-19) · Owner: Claude (product/eng lead for this rebase)
Supersedes for direction: visual language and app structure of the v0.x prototypes. Keeps: product non-negotiables in `CLAUDE.md`, domain knowledge in `src/domain/*`, research in `docs/specs/*`.

이 문서는 "다음 시안"이 아니라 **출시되어 여러 병원과 수천 명이 쓰는 제품**의 기초다. 한 번 내보내면 위치 하나, 문구 하나를 마음대로 바꿀 수 없다는 전제로 결정했다.

---

## 1. 제품 정의

### 1-1. 한 문장

> **Fevio는 난임 병원과 환자 가정 사이의 처방 실행 레이어다.** 병원이 바꾼 처방이 집에서 정확히, 제시간에 실행되게 하고, 그 기록을 다음 진료로 돌려보낸다.

### 1-2. 왜 지금, 왜 이 버티컬

- 체외수정은 2~3일마다 처방이 바뀌고, 하루 여러 번 투약하며, 실행은 병원 밖 가정에서 일어난다. 병원과 가정 사이에 **실행을 추적하는 시스템이 없다.** 종이 스케줄표, 카톡, 전화가 그 자리를 메운다.
- 실행 오류가 흔하다: 투약 일정·용량 혼란 27%, 의사-환자 기록 불일치 20.5% (`docs/specs/care-input-and-dosing-flow.md` §1-2).
- 2024년 시술비 지원 확대로 회차와 환자가 늘었다. 병원의 안내·문의 업무가 늘어나는 구조다.
- 모델이 좋아지면서 "말로 들은 처방"을 구조화하고 짧게 되묻는 일이 실용 수준이 됐다. 이전에는 수동 입력이 너무 무거워서 이 제품이 성립하기 어려웠다. **이게 Fevio 2가 지금 가능한 이유다.**

### 1-3. 누가 돈을 내고 누가 쓰나

| 주체 | 역할 | 얻는 것 |
|---|---|---|
| 병원 (구매자) | 처방 전송, 문의 응답, 진료 전 정리 열람 | 문의 감소, 안내 기록, 투약 오류 감소, 진료 시간 단축, 환자 유지 |
| 환자 (주 사용자) | 처방 확인, 투약 기록, 대화 | 바뀐 처방을 정확히, 놓치지 않게, 혼자 떠안지 않게 |
| 함께 보는 사람 | 같은 일정 보기, 알림, 대신 기록 | 무엇이 언제인지 정확히 앎 |

- **수익 모델 (결정):** 병원 구독. 단가는 '활성 주기'(처방이 진행 중인 환자) 수 기준. 환자는 무료.
- **병원 없이 쓰는 환자 (독립 모드):** 같은 앱. 처방 입력을 대화·사진으로 직접 한다. 병원 영업의 입구 역할이다(환자가 자기 병원에 소개).

### 1-4. 하지 않는 것

진단, 용량 결정, 결과 예측, 치료 추천, 커뮤니티, 광고(투약·결과 화면), 역할 지정, 의료 판단이 들어간 위험도 판정.

## 2. 경험의 뼈대

### 2-1. 다섯 개의 표면

| 표면 | 사용자 | 형태 | 핵심 객체 |
|---|---|---|---|
| **환자 앱** | 환자 | 네이티브 (iOS/Android) | 하루 다이얼, 투약 묶음, 대화 커튼 |
| **함께 보기** | 함께 보는 사람 | 같은 앱의 초대 계정, 또는 웹 링크(읽기 전용) | 같은 하루 다이얼, 알림 |
| **병원 콘솔** | 코디네이터·간호사·의사 | 웹 (데스크톱) | 환자 보드, 처방 전송, 문의함, 진료 전 정리 |
| **병원 설정** | 병원 관리자 | 콘솔 안 | 프로토콜 템플릿, 질문 세트, 경고 규칙, 자료, 운영 시간, 브랜드 |
| **플랫폼 운영** | Fevio | 내부 도구 | 테넌트, 버전, 모델 평가, 사고 대응 |

### 2-2. 환자 앱 구조 (탭 3개, 고정)

```text
[일정]        [오늘]        [기록]
              ↑ 가운데, 기본
위에서 당기기 = 대화 커튼 (모든 탭 공통)
```

- **오늘:** 하루 다이얼 + 다음 투약 묶음. 단계에 따라 중심 객체가 바뀐다(아래 2-3).
- **일정:** 주기 전체(단계 띠) + 주/월. 처방 버전 이력("11.17 병원 전송 · 바뀐 점 2개").
- **기록:** 투약 원장(언제, 누가, 출처), 진료 전 정리 보낸 이력, 병원과의 대화.
- **함께 보는 사람 관리, 병원 연결, 알림 설정**은 기록 탭 상단의 계정 영역에 둔다. 탭을 늘리지 않는다.
- **탭 구조는 출시 후 바꾸지 않는다.** 새 기능은 커튼 대화나 기존 탭 안의 모듈로 들어간다.

### 2-3. 단계별 '오늘'

화면 구성은 클라이언트에 고정된 레이아웃 몇 개 중 하나를 **서버 상태가 고른다.** 병원이 레이아웃을 바꾸지는 못한다(안전과 일관성).

| 상태 | 중심 객체 | 첫 화면 버튼 |
|---|---|---|
| 투약일 | 하루 다이얼 + 다음 묶음 | 맞았어요 (정시 ±창 안에서만 활성) |
| 트리거 당일 | 정각 카운트다운 + 이중 확인 | 확인 두 개 뒤 '맞았어요' |
| 진료일 | 진료 카드(출발, 금식, 준비물) + 진료 전 정리 | 진료 전 정리 보내기 / 진료 뒤 정리 |
| 채취·이식 당일 | 출발 시각, 금식, 동반 | 없음 (정보만) |
| 기다림 | 여백 + 남은 투약 하나 + 판정일 | 0~1개 |
| 결과 보호 | 결과 기록은 사용자가 원할 때만 | 없음. 알림·제안 정지 |

### 2-4. 대화 커튼 (모든 탭 공통)

- 위에서 당기거나 '오늘'의 말풍선을 누르면 열린다. 화면의 약 45%(엿보기) → 입력 시 전체.
- 다섯 가지 대화: 진료 뒤 정리, 투약 확인, 진료 전 인터뷰, 질문하기, 이해 확인 (`docs/specs/agent-interaction-layer.md`).
- 대화는 언제나 **위쪽에 고정된 '정리 중' 초안**을 채운다. 확정은 사용자 버튼.

## 3. 핵심 데이터 모델 (계약)

이 모델은 앱·콘솔·대화가 공유하는 단일 계약이다. 필드 추가는 가능하지만 의미 변경은 새 버전으로만 한다.

```text
Tenant (병원)            id, name, brand { accentHex, logoAssetId }, timezone='Asia/Seoul', config_version
StaffMember              tenantId, role: coordinator | nurse | physician | admin
Patient                  id, tenantId | null (독립), locale
CareCircle               patientId, members[{ userId, relation, scope: 'schedule' | 'schedule+records' }]
Cycle                    id, patientId, tenantId, startedAt, outcome?
CycleEvent (append-only) cycleId, type (period_started … cycle_closed), date, source, confirmedBy
Medication               id, cycleId, name, form, unit (고정), storage?, penCapacity?, catalogRef?
RegimenVersion           id, cycleId, version, items[{ medicationId, dose, times[], start, end }],
                         source: clinic_push | conversation | photo | manual, sourceRef,
                         createdBy, confirmedByPatientAt?, supersedes?
DoseEvent                id, regimenItemRef, scheduledAt (UTC 저장, Asia/Seoul 해석), window,
                         status, doneAt?, administeredBy, recordedBy, confirmedByPatient
Visit                    cycleId, at, fastingFrom?, companionRequired?, notes(source-linked)
PreVisitBrief            visitId, adherenceSnapshot, answers[], questions[], sentAt?
Conversation / Turn      cycleId, intent, turns[], draftRef, modelVersion, promptVersion
ClinicTicket             tenantId, patientId, context{phase, recentDoses, question}, status, sla
ConfigArtifact           tenantId, kind: protocol_template | question_set | alert_rules | content | hours,
                         version, status: draft | approved | live | retired, approvedBy
AuditLog                 actor, action, subject, before?, after?, at
```

원칙:

- **처방은 덮어쓰지 않는다.** 바뀌면 새 `RegimenVersion`. 화면의 '바뀐 점'은 두 버전의 차이에서 계산한다.
- **투약 기록은 지우지 않는다.** 정정은 새 이벤트로 남긴다.
- **시각은 UTC로 저장하고 Asia/Seoul로 해석**한다. 기존 `protocol-draft.ts`의 UTC 버그를 여기서 끊는다.
- **확정 전 데이터는 실행 객체가 아니다.** 알림, 다이얼, 콘솔 지표는 확정된 버전만 쓴다.

## 4. 설정 우선 (Configuration over code)

병원마다 다른 것은 코드가 아니라 **버전이 붙은 설정 산출물**로 만든다.

| 병원이 바꿀 수 있는 것 | 바꿀 수 없는 것 |
|---|---|
| 프로토콜 템플릿 (약 목록, 기본 시각, 증감 단위) | 탭 구조, 레이아웃, 안전 색 |
| 진료 전 질문 세트와 선택지 | 확정 우선 원칙 |
| 경고 규칙 (조건 → 연락 카드 문구·대상) | 모델 가드레일 |
| 승인 자료 (안내문, FAQ) | 결과 보호 모드 동작 |
| 운영 시간, 야간 안내, 연락처 | 알림 단계 (30분 전, 정시, +15, +30)의 존재. 시각만 조정 가능 |
| 브랜드 (로고, 강조색 한 개) | 글꼴, 간격, 컴포넌트 형태 |

수명 주기: `draft → approved(검토자 서명) → live(시점 지정) → retired`. 진행 중인 주기는 시작 당시 버전을 기본으로 따르고, 병원이 명시적으로 이전할 때만 새 버전으로 옮긴다. 모든 전환은 감사 기록에 남는다.

## 5. 플랫폼 구조

```text
apps/patient     React Native (Expo)  — 로컬 알림 예약, 위젯/실시간 현황, 오프라인 원장
apps/console     Next.js               — 병원 콘솔, 병원 설정
apps/link        Next.js (기존 레포)    — 함께 보기 웹 링크, 랜딩, 초대
packages/domain  TypeScript            — 상태 기계, 처방 차이 계산, 투약 펼치기, 규칙 엔진 (순수 함수)
packages/ui      디자인 토큰 + 공통 컴포넌트 명세 (RN / Web 각각 구현, 같은 토큰)
services/api     Supabase (Postgres + RLS, 서울 리전) + Edge Functions
services/agent   대화 조정기 (상태 기계 + 도구), 모델 호출은 서버만
services/notify  APNs/FCM 발송, 미확인 재알림, 함께 보는 사람 알림
```

결정과 이유:

- **환자 앱은 네이티브.** 이 제품의 가치는 "정해진 순간에 먼저 찾아가기"다. iOS 웹앱은 홈 화면 추가 없이는 푸시가 안 되고, 공유 받기와 잠금화면 표시가 안 된다(`docs/specs/care-input-and-dosing-flow.md` §8). **알림은 기기에서 로컬로 예약**하고 서버 푸시는 처방 변경 반영과 재알림에 쓴다. 네트워크가 끊겨도 주사 알림은 울린다.
- **도메인 로직은 하나.** 앱, 콘솔, 대화, 알림이 같은 `packages/domain`을 쓴다. 현재 레포의 `cycle-state-machine.ts`, `line-split.ts`, 테스트는 여기로 옮긴다.
- **현재 Next.js 앱**은 함께 보기 링크와 웹 진입점으로 남긴다. 환자 화면 코드는 새로 만든다.

### 5-1. 신뢰성

| 위험 | 대응 |
|---|---|
| 처방 변경 후 기기 알림이 옛 시각에 울림 | 처방 버전이 바뀌면 서버가 무음 푸시로 재동기화 요청, 앱은 열릴 때마다 버전 대조. 버전 불일치 시 오늘 화면 상단에 '새 처방 확인 필요' |
| 중복 기록 | `DoseEvent`는 (regimenItem, scheduledAt) 고유. 기록 요청은 멱등 |
| 시간대 | 저장 UTC, 해석 Asia/Seoul. 해외 체류 시에도 병원 시각 기준으로 표시하고 기기 시각을 병기 |
| 오프라인 | 원장은 로컬 우선 기록 후 동기화. 충돌 시 서버가 시간 순 병합하고, 둘 다 남긴 뒤 환자 확인 |
| 모델 장애 | 대화 커튼은 정해진 질문 목록 모드로 자동 전환. 수동 입력 화면은 항상 동작 |

### 5-2. 출시 운영

- 기능 플래그(테넌트·비율 단위), 단계적 배포, **킬 스위치**(대화 모델, 사진 인식, 병원 전송 각각).
- 앱 최소 지원 버전 강제: 안전 관련 변경은 강제 업데이트 공지.
- 관측: 알림 발송→표시→기록 깔때기, 확정 지연, 모델 응답 시간·형식 실패율, 콘솔 응답 시간.
- 사고 등급: S1(투약 알림 누락·오발송) 15분 내 대응, 병원 공지 템플릿 준비.

## 6. 모델 운영 (대화 커튼)

- **역할:** 추출(말·사진·텍스트 → `RegimenDiff`), 되묻기 선택(정해진 목록), 승인 자료 검색·인용, 문의 요약.
- **하지 않음:** 용량·진단·위험도 판단. 위험 신호는 병원 규칙 엔진이 판정한다.
- **버전 관리:** 프롬프트·도구 정의·모델 ID를 버전으로 묶어 `Conversation`에 기록한다.
- **평가 세트:** 익명화된 진료 안내 문장 500개 이상의 정답 세트를 만든다. 지표는 항목별 추출 정확도, 단위 오류 0건, '모르겠음' 처리 정확도. 출시 기준: 단위 오류 0, 용량 오추출 0, 날짜·시각 정확도 98% 이상. 미달 항목은 되묻기로 강제한다.
- **데이터:** 처방·증상 대화가 모델로 가므로 별도 동의, 처리 위탁 계약, 국외 이전 고지가 필요하다. 병원 콘솔에서 테넌트별로 모델 사용을 끌 수 있다.

## 7. 규제와 신뢰

- **포지셔닝:** 병원 지시 전달·기록·알림 도구. 진단·치료 판단 기능이 없어야 의료기기에서 벗어날 수 있다. 식약처 디지털의료제품 분류 검토를 출시 전 게이트로 둔다.
- **개인정보:** 건강정보는 민감정보. 수집 동의 분리(필수: 처방·투약 / 선택: 대화 모델 처리, 함께 보는 사람 공유, 병원 전송). 국내 리전 저장. 감사 기록 5년 보관(병원 계약에 따라).
- **콘텐츠 책임:** 약 준비 안내와 자료는 허가 사용설명서 또는 병원 승인본만. 출처 표시는 필수.
- **결과 보호:** 음성 결과 기록 시 모든 제안·알림(투약 외)·광고 정지. 판매·업셀 화면 금지.

## 8. 디자인 시스템: "원장과 신호 (Ledger & Signal)"

이전 시안의 세이지·크림·코랄·라벤더 팔레트는 쓰지 않는다. 새 시스템은 두 생각에서 나온다.

1. **원장(Ledger):** Fevio가 보여주는 모든 것은 병원 처방이나 사용자 확인에서 온 **기록**이다. 그래서 화면은 장부처럼 정확해야 한다. 가는 선, 고정폭 숫자, 출처 표시, 시간 순서.
2. **신호(Signal):** 색은 장식이 아니라 **지금 행동해야 하는 것** 하나에만 쓴다. 나머지는 잉크와 종이다.

### 8-1. 토큰

| 토큰 | 값 | 쓰임 |
|---|---|---|
| paper | #FFFFFF | 카드, 시트 |
| canvas | #F4F4F5 | 앱 배경 |
| ink | #0E0F11 | 본문, 기본 버튼 |
| ink-2 | #575A62 | 보조 글자 |
| ink-3 | #8A8D94 | 메타 (12px 이상, 대비 확인) |
| hairline | #E4E4E7 | 구분선 |
| signal | #1F5BFF | 지금·다음 (다이얼 바늘, 다음 묶음, 활성 버튼) |
| alert | #D92D20 | 병원 경고 규칙 결과에만 |
| tenant-accent | 병원 지정 1색 | 병원 로고 칩, 병원 메시지 테두리에만. 안전 의미 색과 겹치면 자동 대체 |

- **초록·핑크·보라는 시스템 색으로 쓰지 않는다.** 완료는 색이 아니라 잉크 채움과 체크로 표시한다.
- 다크 모드는 같은 의미 체계로 1차 출시에 포함한다(야간 투약 때문).

### 8-2. 글자

- 한글·라틴 모두 Pretendard. 시각·용량은 tabular 숫자.
- 숫자 위계: 다음 시각 56, 용량 28, 본문 17, 메타 13. 큰 글자는 '시간'과 '용량'에만 쓴다.

### 8-3. 서명 객체: 하루 다이얼

- 하루 24시간 원. 위가 자정, 시계 방향.
- 투약 시점: 눈금(끝난 것은 잉크로 채움, 다음 것은 signal 색 굵은 눈금).
- 지금: signal 색 바늘.
- 가운데: 다음 묶음 시각, 남은 시간, 약 개수.
- 다이얼은 '진행률'을 그리지 않는다. 달성률 링은 만들지 않는다.

### 8-4. 컴포넌트 (명세 수준으로 고정)

| 컴포넌트 | 상태 | 규칙 |
|---|---|---|
| DayDial | 투약일 / 트리거 / 투약 없음 | 눈금 최대 8개. 겹치면 묶음으로 합침 |
| DoseBundle | 예정 / 열림(창 안) / 완료 / 재확인 / 놓침 | 약마다 체크. '모두 맞았어요'는 창 안에서만 |
| DoseLine | 기본 / 첫 펜 / 희석 필요 / 펜 교체 | 용량+단위 크게, 형태 아이콘, 출처 칩 |
| SourceChip | 병원 전송 / 대화 / 사진 / 직접 | 모든 처방 줄에 표시 |
| CurtainAgent | 닫힘 / 엿보기 / 펼침 | 상단 초안 고정, 칩 2~4개, '모르겠어요' 필수 |
| DraftTray | 비어 있음 / 채우는 중 / 확정 가능 / 확정됨 | 빈칸 '?' 표시, 확정 버튼은 빈칸 없을 때만 |
| ChangeRow | 용량 / 추가 / 중단 / 시각 / 진료 / 금식 | 이전→이후 함께 표시 |
| ClinicCard | 연락 / 답변 / 경고 | tenant-accent 테두리, 운영 시간 표시 |
| LedgerRow | 정시 / 지연 / 놓침 / 정정 | 시각, 누가 놨는지, 누가 기록했는지 |

### 8-5. 움직임

- 기능이 있을 때만 움직인다: 바늘은 분 단위로 이동, 커튼은 손가락을 따라오고 놓으면 스프링으로 멈춤, 확정 시 초안 칸이 원장 줄로 내려가며 접힘.
- 장식 반복 애니메이션은 쓰지 않는다.

### 8-6. 말투

짧고 정확하게, 판단하지 않는다. "지금 맞을 시간 · 3개", "아직 확인 안 됐어요", "병원 안내를 따라야 해요". 위로·격려·예측 문장은 쓰지 않는다.
